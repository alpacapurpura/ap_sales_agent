Basado en el análisis de tu arquitectura, he identificado **2 errores críticos** que detendrán tu aplicación en producción y varios riesgos operativos importantes.

### 🚨 Errores Críticos (Deben corregirse antes del despliegue)

1.  **Frontend sin conexión a API (Build Time vs Runtime):**
    *   **Error:** Next.js "quema" (hardcodea) las variables `NEXT_PUBLIC_` en el código JS durante el *build*. Tu `Dockerfile` actual no recibe `NEXT_PUBLIC_API_URL` como argumento de construcción (ARG), solo la clave de Clerk.
    *   **Consecuencia:** En producción, el frontend intentará conectarse a `undefined` en lugar de tu API, rompiendo toda la funcionalidad.
    *   **Solución:** Debemos agregar `ARG NEXT_PUBLIC_API_URL` al `frontend/Dockerfile` y pasarla en `docker-compose.yml`.

2.  **Incompatibilidad de WhatsApp (Evolution API):**
    *   **Error:** Usas `v1.8.2` (archivos) en desarrollo y `v2.2.2` (Postgres) en producción.
    *   **Consecuencia:** La v2 cambia drásticamente la estructura de base de datos y autenticación. Es muy probable que tu integración falle o pierda sesiones al desplegar.
    *   **Solución:** Recomiendo encarecidamente usar la misma versión en ambos entornos o probar la migración localmente primero.

### ⚠️ Riesgos Operativos

1.  **Downtime por Build en Servidor:**
    *   Hacer `git pull` y luego `docker compose up --build` consumirá mucha CPU/RAM en tu servidor Linux durante 3-5 minutos (compilación de Next.js), dejando el servicio inactivo (503 Service Unavailable) durante ese tiempo.
2.  **Migraciones de Base de Datos:**
    *   Al desplegar código nuevo con cambios en modelos, la base de datos no se actualiza sola. Necesitas ejecutar `alembic upgrade head` manualmente o la API fallará con errores de "column not found".
3.  **Red Externa:**
    *   El despliegue fallará si no ejecutas `docker network create web_gateway` manualmente en el servidor antes del primer `docker compose up`.
