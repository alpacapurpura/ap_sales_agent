Actualmente **no se está utilizando una estructura de carpetas segregada por Tenant**, lo cual no es ideal para una arquitectura multi-tenant (SaaS).

### Estado Actual vs. Estado Ideal

1.  **Estado Actual:**
    *   **Offer Gallery:** `static/offers/{offer_id}/gallery/{uuid}.jpg` (Mezcla tenants si no se controla el acceso al `offer_id`).
    *   **Brand Gallery:** `static/gallery/{tenant_id}_{uuid}.jpg` (Todo en una carpeta gigante, difícil de migrar o limpiar).

2.  **Estado Ideal (Propuesta S3-Ready):**
    La mejor práctica, pensando en una futura migración a AWS S3 y seguridad, es usar el `tenant_id` como la "raíz" lógica de almacenamiento (o "bucket prefix").
    *   Estructura: `static/{tenant_id}/{module}/{resource_id}/file.ext`

### Plan de Refactorización

Voy a reestructurar el sistema de almacenamiento para que sea **Multi-Tenant First**. Esto facilitará enormemente la migración futura a S3 (simplemente se sincroniza la carpeta del tenant) y mejora la seguridad.

1.  **Refactorizar `Offer Gallery`**:
    *   Cambiar ruta a: `static/{tenant_id}/offers/{offer_id}/gallery/`
    *   Actualizar lógica de subida y borrado en `backend/src/api/routers/offer_gallery.py`.

2.  **Refactorizar `Brand Gallery`**:
    *   Cambiar ruta a: `static/{tenant_id}/brand/gallery/`
    *   Eliminar el prefijo `{tenant_id}_` del nombre de archivo, ya que estará implícito en la carpeta.
    *   Actualizar `backend/src/api/routers/gallery.py`.

3.  **Migración de Datos (Script)**:
    *   Crearé un pequeño script utilitario (o función en el startup) para mover las imágenes existentes a la nueva estructura si se detectan en la ubicación antigua, para no romper las imágenes que acabamos de subir.

Esta estructura es el estándar de industria para SaaS: aísla completamente los datos de cada cliente a nivel de sistema de archivos.
