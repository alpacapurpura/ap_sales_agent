# Plan de Implementación Técnica: Dashboard "Centro de Comando"

Para cumplir con los requisitos de robustez, abstracción y mantenibilidad, implementaremos el dashboard siguiendo una arquitectura de **Capas Aisladas (Layered Architecture)**. Esto asegura que cambios en los modelos de base de datos no rompan la interfaz de usuario.

## 🏗️ Fase 1: Backend (Abstracción y Lógica de Negocio)

En lugar de exponer modelos crudos (Lead, User) al frontend, crearemos una capa intermedia de **DTOs (Data Transfer Objects)** y un **Servicio de Agregación**.

### 1.1. Definición de Esquemas (DTOs)
**Archivo:** `backend/src/core/domain/dashboard_schema.py`
Crearemos modelos Pydantic estrictos que definan el "Contrato" del dashboard.
- `DashboardMetrics`: Valores numéricos (pipeline, conversión).
- `ActionItem`: Abstracción de tareas (sea un chat, un error o una cita).
    - *Ventaja:* El frontend no necesita saber si una tarea viene de WhatsApp o Telegram, solo recibe un `ActionItem`.

### 1.2. Servicio de Dashboard
**Archivo:** `backend/src/services/dashboard_service.py`
Este servicio actuará como orquestador.
- **Función:** `get_summary(tenant_id)`
- **Lógica:** Consultará `LeadRepository`, `CalendarRepository` y `KnowledgeService` en paralelo.
- **Transformación:** Convertirá los datos crudos en `ActionItems`.
    - *Ejemplo:* Si `Lead.status == 'human_help'`, genera un `ActionItem(type='INTERVENTION', priority='HIGH')`.

### 1.3. API Router
**Archivo:** `backend/src/api/routers/dashboard.py`
Endpoint limpio `GET /api/v1/dashboard/summary`.

---

## 🎨 Fase 2: Frontend (Composición y Resiliencia)

Usaremos el patrón de **Componentes Inteligentes** y **Manejo de Errores Granular**.

### 2.1. Capa de Datos (Hooks & Types)
**Archivos:** `frontend/src/features/dashboard/types.ts` y `lib/api/dashboard.ts`
- Definición de interfaces TypeScript que espejan los DTOs de Python.
- Hook `useDashboardSummary()` para manejo de estado de carga y error.

### 2.2. Arquitectura de Componentes (Bento Grid)
**Directorio:** `frontend/src/features/dashboard/components/`
Crearemos widgets aislados. Si uno falla, no rompe toda la página.
1.  `MetricCard.tsx`: Componente genérico para KPIs (Pipeline, Conversión).
2.  `WarRoomWidget.tsx`: Lista de `ActionItems` interactiva.
3.  `AgendaWidget.tsx`: Visualización de próximas citas.
4.  `FunnelChart.tsx`: Visualización del embudo (usando Recharts si es necesario, o CSS puro).

### 2.3. Integración
**Archivo:** `frontend/src/app/(dashboard)/page.tsx`
Reemplazo total de la página actual. Implementará un **Bento Grid Layout** responsivo (CSS Grid) que aloja los widgets.

---

## 🛡️ Estrategia de Robustez y Documentación

1.  **Anti-Fragilidad:**
    - Backend: Los DTOs usarán `extra='ignore'` para no romper si se añaden campos a la DB en el futuro.
    - Frontend: Cada Widget tendrá un `ErrorBoundary` implícito (o manejo de estado `error` individual) para que un fallo en "Agenda" no oculte "Ingresos".

2.  **Documentación:**
    - **Docstrings:** Cada método del servicio explicará la regla de negocio (ej: *"Calcula pipeline sumando leads con status > QUALIFIED"*).
    - **README:** Generaré un `frontend/src/features/dashboard/README.md` explicando la arquitectura de componentes.

## 📝 Pasos de Ejecución
1.  **Backend:** Crear Schema y Service.
2.  **Backend:** Crear Router y registrarlo en `main.py`.
3.  **Frontend:** Crear Tipos y Cliente API.
4.  **Frontend:** Implementar Widgets base.
5.  **Frontend:** Ensamblar Bento Grid en `page.tsx`.
