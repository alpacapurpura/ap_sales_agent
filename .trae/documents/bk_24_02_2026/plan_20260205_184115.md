# Plan de Ejecución: Integración y Poblado de Datos

He actualizado el plan para incluir la fase crítica de **Migración de Datos (Seeding)** que solicitaste. Esto asegurará que al abrir cualquier oferta existente, el formulario "explotará" de información correcta en lugar de romperse.

## 1. Fase de Datos (Backend & Seeding)
**Objetivo**: Garantizar que cada oferta en la DB tenga `specific_details` coherentes con su arquetipo.

1.  **Script de Poblado (`backend/scripts/seed_offer_details.py`)**:
    *   Escribiré un script en Python que recorra todas las ofertas existentes.
    *   Detectará el `type` de cada una (ej. `LUXURY_RETREAT`).
    *   Generará data ficticia válida para ese esquema (ej. `venue_name="Hotel X"`, `start_date=...`).
    *   Guardará los cambios en PostgreSQL.
2.  **Endpoint de Metadatos**:
    *   Crear endpoint para servir `OFFER_METADATA` al frontend (necesario para los Hints).

## 2. Fase Frontend (Componentes y Lógica)
**Objetivo**: Construir la interfaz polimórfica en `offer-studio`.

1.  **Zod Schemas**: Definir los esquemas estrictos en TypeScript para `EventDetails`, `SubscriptionDetails`, etc.
2.  **Componentes UI Educativos**:
    *   `RichEnumSelect`: Selectores visuales (Tarjetas).
    *   `ContextualHint`: Tooltips inteligentes.
3.  **Fábrica de Formularios**:
    *   Crear `EventForm` y `SubscriptionForm`.
    *   Actualizar `ProductForm`, `ServiceForm`, `ProgramForm`.
    *   Implementar `PolymorphicFactory` en `SpecificDetailsStep`.

## 3. Fase de Integración
1.  **Conexión**: Asegurar que `OfferEditor` pase la data correcta al Factory.
2.  **Validación**: Ejecutar el script de seeding y verificar que el frontend cargue los datos sin errores.

Voy a proceder primero con el script de backend para "sanar" tu base de datos antes de tocar el frontend.
