def upgrade() -> None:
    # 1. Backup snapshot (idempotent — drop if exists then recreate).
    op.execute("DROP TABLE IF EXISTS model_pricing_snapshot_backup_pre_t3")
    op.execute(
        "CREATE TABLE model_pricing_snapshot_backup_pre_t3 AS "
        "SELECT * FROM model_pricing_snapshot",
    )
    # 2. Repair historical mis-tagged rows.
    # provider='openai' AND model LIKE non-openai prefix → re-tag.
    op.execute("""
        UPDATE model_pricing_snapshot
        SET provider = 'deepseek',
            model = CASE WHEN model LIKE 'deepseek/%' THEN model
                         ELSE 'deepseek/' || model END
        WHERE provider = 'openai'
          AND (model LIKE 'deepseek%' OR model LIKE '%deepseek%')
    """)
    # ... similar for kimi, qwen ...

## 14. Free-form notes — what I'd tell a smart colleague

**T-3 is a surgical data repair with near-zero risk.** Here's what I'd flag:

1. **Backup table is your insurance.** The `model_pricing_snapshot_backup_pre_t3` CTAS is atomic and instantaneous (< 1s on small snapshot table ~100-500 rows). The downgrade path uses it to restore state. Test this roundtrip rigorously in your migration_test clone DB — the acceptance A4 test must run downgrade and verify row counts match. If downgrade fails in prod, you'll want to know immediately.

2. **The UPDATE patterns are safe but textual.** You're matching mis-tagged rows via `provider='openai' AND model LIKE 'deepseek%' OR 'kimi%'` etc. This is correct per the spec (historical data was tagged wrong). BUT: verify no false positives by running a dry-run SELECT with the same WHERE clause against prod backup first (off-hours window). Chris likely will do this pre-release, but mention it if the builder asks.

3. **Idempotency is non-negotiable.** The acceptance A1 test (`alembic upgrade head && alembic upgrade head`) is not a nice-to-have — it's MANDATORY. If you forget the `IF NOT EXISTS` on the backup table drop or the `CASE WHEN model LIKE 'deepseek/%' THEN model` logic (to avoid double-slashing), the 2x upgrade will fail and you'll block the entire sprint. Double-check this in your RED phase tests.

4. **No schema change = no cross-module blast radius.** T-3 is data-only. The ORM model, repo interface, and all consumers stay unchanged. This is why downstream regression scope is limited to the cost/pricing tests. Zero UI impact. Simplicity is good.

5. **Backup table naming convention is NEW — document it.** You're introducing `*_backup_pre_tN` pattern (pre_t3, later pre_t6a, pre_t6c). Future migrations will copy this. If the pattern is good (simple, clear), mention it in the 05-impl result so the next builder (T-6) can cite precedent. If you discover edge cases (e.g., backup table bloats, needs cleanup), document that too for T-6 architects to consider.

6. **No TDD pitfall here, but be deliberate.** The migration code is 100% procedural SQL — no business logic, no ORM. Your RED phase is writing test fixtures that clone the DB, insert stale data, run migration, verify state. This is different from typical TDD (no unit test for pure SQL). Lean on the `migration_test_db` fixture provided by the harness; don't reinvent the wheel.

7. **Depends-on T-1 + T-2 are already merged.** You don't need to wait. T-1 (cost_recorder) and T-2 (sync-pricing) established the canonical provider derivation pattern. T-3 just backfills. Start immediately; expect quick merge to `development` after auditor sign-off.
