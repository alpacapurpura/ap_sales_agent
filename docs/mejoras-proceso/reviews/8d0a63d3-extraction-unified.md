# Review: 8d0a63d3 — unified guided-aware extraction flow

**Fecha**: 2026-04-23
**Veredicto**: CHANGES_REQUIRED
**Score**: 7/10

## Summary
Corrige el bug real (loop de 8 `extract_structured` en guided) con un enfoque sólido: extraction toolset desbloqueado en guided, nueva JSONB sibling `active_extraction_job`, prompt con dos bloques condicionales, orchestrator offer con paridad brand, trace table nueva. La lógica de estado (`active_job_state.py` + persistence), reescritura del prompt Jinja y el alineamiento del `poll_endpoint` con el mount `/api/v1/{module}/tools` son correctos. Sin embargo, el `OfferExtractionOrchestrator` introduce **duplicación de llamadas LLM (3 extras por extracción full)** y **desajuste semántico entre section slugs y modelos Pydantic** — problema de correctness que impacta costo y datos persistidos. Además, varias capas de persistencia nuevas carecen de filtro `tenant_id` en el SELECT (mismo patrón pre-existente en `guided/persistence.py`, pero se amplifica aquí).

## Findings

### CRITICAL

- **`backend/src/modules/offer/application/offer_extraction_orchestrator.py:1300-1312,1336-1344,1366-1375,1420-1430`** — Duplicación de llamadas LLM y mismatch semántico.
  - W1 llama `_extract_promise` dos veces (índice 0 "promise" y 2 "identity"), usando el resultado del índice 0 para ambos (luego descarta el 2).
  - W2 mapea slug "pricing" al método `_extract_closing` (retorna `OfferClosingUpdate` — guarantee, checkout, onboarding — no pricing fields).
  - W3 llama `_extract_closing` otra vez (ya se llamó en W2) y `_extract_strategy` otra vez (ya se llamó en W1) bajo slugs "closing_system" y "classification". `_extract_details` bajo slug "onboarding".
  - En `_run_single_wave` el patrón se repite: 9 coroutines para 9 slugs pero con sólo 6 métodos reales (`promise`×2, `strategy`×2, `closing`×2, `psychology`, `value_stack`, `details`).
  - **Impacto**: cada extracción offer full dispara ~3 llamadas LLM extras innecesarias (gasto TPM + tiempo), y el evento `section_completed` + nav pill emitidos para "identity", "pricing", "classification" apuntan a datos inconsistentes con su nombre. `_announce_sections` recibe `[promise_result, promise_result, strategy_result]` para `["identity", "promise", "strategy"]` — dos pills con el mismo delta bajo dos slugs.
  - **Fix**: alinear waves con los extractores reales. Opciones:
    1. Consolidar slugs (sin identity/pricing/classification virtuales): W1=[promise, strategy]; W2=[psychology, value_stack, closing]; W3=[details]. Coincide con la versión previa del servicio que funcionaba.
    2. Si las secciones nuevas son necesarias, crear extractores dedicados (`_extract_identity`, `_extract_pricing`, `_extract_onboarding`, `_extract_classification`) con prompts y modelos Pydantic específicos. No reutilizar el mismo método bajo slugs distintos.
  - El design doc (§ "Waves offer") no indicó reutilizar extractores; la implementación desvió sin documentarlo.

### HIGH

- **`backend/src/modules/copilot/application/extraction/active_job_persistence.py:30-45, 56-77`** — `SELECT/UPDATE ... WHERE id = :id` sin filtro `tenant_id`. La regla `tenant-isolation.md` exige que toda query incluya `tenant_id`. Ya existe el mismo patrón en `guided/persistence.py` (pre-existente, no introducido aquí), pero este commit lo duplica. `conversation_id` es una UUID y no es adivinable, pero la regla es "ALL queries filter `tenant_id`" sin excepción. Agregar `AND tenant_id = :tenant_id` en ambas queries y recibir el tenant como parámetro (o inyectar via `get_tenant_id()` del context).
- **`backend/src/modules/copilot/application/orchestrator/chat.py:515-539`** — `_read_procedure_state` mismo issue: `WHERE id = :id` sin `tenant_id`. Corregir alineado con el fix anterior.
- **`backend/src/modules/copilot/application/extraction_card_flow.py:431-434, 462-466`** — Subscriber crea `TraceRecorder` pasando `UUID(str(event.tenant_id))`. Si `event.tenant_id` viene ya como UUID, `str()` → `UUID()` es redundante; si viene como string, funciona. Más importante: **no hay manejo si `event.tenant_id` es `None`** — el constructor de `UUID(None)` explota. `try/except Exception` externo lo atrapa pero se pierde el trace sin warning específico. Agregar guard temprano.
- **`backend/src/modules/offer/application/offer_extraction_orchestrator.py:1485-1503`** — `_merge_and_save` acumula `merged` vía `result.model_dump(exclude_unset=True, exclude_none=True)`, pero cuando los mismos campos vienen de dos extractores distintos (ej. `promise_result` aplicado dos veces en W1), la segunda escritura pisa la primera silenciosamente. Peor, con `patch_offer(merged)` recibiendo `headline_promise` dos veces del mismo modelo, la semántica es ambigua. Relacionado con el CRITICAL: al corregir duplicación se resuelve colateralmente.
- **`backend/src/modules/offer/application/offer_extraction_orchestrator.py:1495-1503`** — `logger.exception("offer_extraction_merge_section_failed", error=str(e))` dentro de un `except Exception as e` bare, sin re-raise. El diseño dice "All exceptions are swallowed per-result so partial wave failures don't abort the entire extraction", pero no diferencia entre errores transitorios (timeout LLM) y bugs (TypeError, KeyError en model_dump). Agregar filtro por tipo: `except (pydantic.ValidationError, AttributeError)` para no ocultar bugs.
- **Coverage missing — `_record_active_extraction_job` (`extraction_tools.py:115-162`)** — Helper nuevo sin test propio. Los tests de `active_job_state.py` cubren la dataclass, pero no el comportamiento de "best-effort persist post-dispatch, read guided state, copy paused_at_block". Regla TDD-mandatory dice test antes código. Agregar test con mocks de `read_guided_state` + `write_active_job`.
- **Coverage missing — `_compute_pending_field_paths` (`orchestrator/graph.py:197-233`)** — Lógica nueva no trivial (split por `.`, fallback por TypeError, fallback por Exception). Sin test. Este es el motor del "no re-preguntar campos llenos" — si falla silenciosamente devuelve la lista completa (ok) pero si tiene bug de path-splitting afecta directamente la UX del bug que originó el commit.

### MEDIUM

- **`backend/src/modules/offer/workers/tasks.py:162-178`** — `OfferExtractionTraceCollector` se construye con `db, tenant_uuid, job_id, mode, url` pero nunca se llama `trace.finish()` desde el worker. El orchestrator lo llama desde dentro (`run()` método). Sin embargo, si `service.extract_all` lanza excepción antes de llegar a `trace.finish(status="completed", ...)`, la fila `offer_extraction_traces` queda con `status='running'` huérfana. Agregar `try/finally trace.finish(status="failed", error_message=str(exc))` en el worker.
- **`backend/src/modules/offer/application/offer_extraction_orchestrator.py:1210-1212`** — `trace.finish(status="completed", sections_succeeded=total_sections)` cuenta 9 secciones siempre como exitosas incluso si alguna falló en el wave. Debe contar secciones cuyo `result` no es `BaseException` ni `None`. Correlaciona con CRITICAL (si los slugs duplicados se arreglan, `total_sections` también).

La regla `backend-quality.md` dice "SQLA 2.0 syntax: `mapped_column`". El modelo brand probablemente tenga el mismo patrón legacy, pero nuevo código debería usar `Mapped[...]` + `mapped_column(...)`. ## Strengths

- **Diseño documentado ANTES**: `copilot-extraction-unified-design.md` (405 líneas) con decisiones acordadas, state contract, flujo de 3 fases, orden de ejecución, success criteria. Cumple TDD/process. El commit es trazable al diseño.
- **Idempotencia migración 060**: `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, downgrade `DROP IF EXISTS`. Sigue regla `backend-migrations.md` al pie de la letra.
- **Best-effort persist en dispatch**: `_record_active_extraction_job` envuelto en try/except + log estructurado. Nunca revierte dispatch. Documentado explícitamente ("a persistence glitch must never revert a successful dispatch"). Correcto para resilience.
- **Test de regresión con referencia a traza**: `test_guided_toolset_includes_extraction.py` cita traza `376850f5-...` en docstring, explica el bug (loop 8×). Followup directo al systematic-debugging.
- **Single DB read per turn**: `_read_procedure_state` consolidado en `chat.py` para hidratar ambos siblings (`guided_state` + `active_extraction_job`) con una sola query. Comentario justifica ("Two reads hit the connection pool twice"). Optimización correcta.
- **Per-wave save invariant** (excepto por el CRITICAL de duplicación): el principio "save before announce" está protegido por tests en `test_extraction_orchestrator_per_wave_save.py` incluyendo orden de ejecución (`execution_order` list trick). 23+ tests con cobertura amplia.
- **Prompt Jinja con dos bloques condicionales**: permite `guided` activo sin `active_extraction_job`, `active_extraction_job` sin `guided`, ambos, o ninguno. Matriz bien cubierta.
- **FastAPI app-level `redirect_slashes=False`** ya en `main.py:157` — no regresión.
- **Tenant isolation en datos de negocio**: `offer_repo.get_by_id(tenant_uuid, offer_uuid)` en worker y `patch_offer(self.offer_id, self.tenant_id, ...)` en orchestrator mantienen el filtro tenant. El gap está sólo en `copilot_conversations.procedure_state` reads (HIGH, patrón pre-existente).
- **Trace collector paridad brand**: `OfferExtractionTraceCollector` tiene métodos crawl_start, crawl_end, wave_start, wave_pause, section_start, section_success, section_failed, merge_start, merge_end, finish. Port fiel.
