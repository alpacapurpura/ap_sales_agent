## Failures + root cause + fix aplicado

### B1 (nuevo) — ARQ task `regen_brand_summary` no commitea → row no persiste

- **Síntoma:** Worker logs reportaban `brand_summary_persisted version=2 chars=624` después de PATCH /api/v1/brand/settings, pero `SELECT * FROM brand_summary WHERE tenant_id=...` seguía mostrando version=1 con `updated_at` viejo. PATCH retornaba 200, evento se emitía, worker corría, pero el row jamás se actualizaba en DB.
- **Trace evidence:**
  - Brain log: `brand_repo_saving` + `brand_repo_saved_verified` ✅.
  - Worker log: `brand_summary_persisted` ✅.
  - DB: row sin cambios.
- **Root cause:** `src/shared/workers/brand_summary_regen.py::regen_brand_summary` (ARQ entrypoint async) abre la session via `db_factory()`, llama `regen_brand_summary_sync(db=db, ...)` (que sólo hace `repo.upsert(...).flush()`), y cierra la session via `db.close()` **sin commit**. SQLAlchemy `close()` sin commit = rollback. Worker observable status "persisted" venía del log dentro de `regen_brand_summary_sync` que asume que el caller commitea — admin Streamlit + backfill script efectivamente commitean, pero el ARQ wrapper no lo hacía.
- **TDD fix:**
  - **RED:** `tests/shared/workers/test_brand_summary_regen.py::{test_arq_wrapper_commits_after_successful_regen, test_arq_wrapper_does_not_commit_when_regen_skipped, test_arq_wrapper_rolls_back_when_sync_raises}` con `_SessionCommitSpy` que cuenta `commit/rollback/close` calls. Pre-fix: `commits == 0`, falla.
  - **Fix arquitectónico:** `regen_brand_summary` ahora envuelve la llamada en try/except: commit cuando `summary is not None`, rollback en cualquier excepción (re-raise), `close` siempre en finally. Anchor [COPILOT-BRAND-SUMMARY-F3] preservado, comment explica regresión TP2.
  - **GREEN:** 3/3 nuevos tests pass. Suite full (591 tests: brand_summary_regen + brand_summary_repository + event_handlers + tests/architecture) verde.
- **Verificación runtime:** post-fix, worker restart + nuevo PATCH → version=2, chars=580, `last_section_changed='brand'`, `updated_at` refreshed. Result key ARQ stale (de la corrida pre-fix) bloqueaba re-enqueue por dedupe — limpieza explícita de `arq:result:brand_summary_regen:{tenant}` documentada en este reporte como guardrail (resolver el bug del worker NO retroactiva los result keys, bloqueante hasta que ARQ keep_result expira ~1h).

### Anomalía A1 (no es bug, design observation) — Lighthouse no se inyecta en `/dashboard`

- **Síntoma:** S2.2 inicial (route `/dashboard`) → no `## Brand Lighthouse` en system prompt. brand_summary populated, sí. Tenant tiene brand. Inicialmente parecía bug.
- **Root cause:** F3 design explícito en `src/modules/brand/copilot_provider/context_inject.py::_INJECTION_SEGMENTS = ("offer-studio", "landing", "campaign", "sales", "growth-studio")`. `/dashboard` y `/brand-studio` excluidas. Doc del injector: "Brand Studio itself doesn't need the lighthouse since the user is editing the source." Dashboard no entra porque la heurística prioriza superficies donde "brand coherence matters most".
- **Tensión vs misión TP2:** la misión enunciada decía "lighthouse always-on en system prompt sin que el user lo pida". La implementación es route-gated por design para minimizar prefix bloat fuera de las superficies donde la marca es action-driver. NO es bug; es decisión documentada en F3 learnings.
- **Recomendación F-pos** (ver §Recomendaciones): si TP4/TP6 evidencian degradación brand cuando el user chatea desde `/dashboard` con intent de marketing, considerar:
  - (a) Incluir `/dashboard` en allowlist (paga prefix bloat ~700 chars en TODOS los chats).
  - (b) Heurística por intent (LLM clasificador detecta que el msg involucra brand → activar lighthouse) — más caro, más preciso.
  - (c) Status quo + redirigir UX al user a una studio cuando intent es brand-touching.

## Recomendaciones (ordenadas por urgencia)

1. **(F-pos arquitectónico, scope reducido)** Considerar agregar `dashboard` (o un sub-segmento como `dashboard/copilot`) al `_INJECTION_SEGMENTS` allowlist si TP4/TP6/TP11 reportan degradación brand_coherence cuando el user pide "ideas para mi marca" desde la home. Costo: ~700 chars adicionales en todos los chats sin uso de marca (cache friendly, sólo paga 1 vez cross-tenant). Beneficio: lighthouse alcanza superficies de descubrimiento.
2. **(F-pos data hygiene)** Agregar admin Streamlit button "regenerate ALL brand_summaries" + cron weekly que recorra tenants con `brand_settings` populated pero `brand_summary` vacío (heredado F3 backfill nunca corrió en prod). Sin este script, cualquier tenant onboarded antes del cierre de F3 sigue sin lighthouse hasta que edite manualmente brand.
3. **(F-pos observability)** El bug B1 hubiera sido invisible al monitor, ya que `brand_summary_persisted` log vino del recorder pero el COMMIT nunca corrió. Recomiendo agregar metric `brand_summary_persistence_lag_seconds` que mide tiempo entre `brand_summary_persisted` log y la próxima vez que el row aparece en SELECT. Si >10s, alertar (race condition u otra commit-missing regression).
4. **(TP3 hint)** `pin_to_memory` (tool del próximo TP) tiene su propio path ARQ-driven posiblemente — auditar `regen_*` o cualquier worker que persista. Patrón: si el sync helper sólo hace `flush`, el async wrapper DEBE commit. Aplicar el mismo `_SessionCommitSpy` pattern para nuevos workers.
5. **(billing infra heredado TP1)** Tier OpenAI sigue afectando — para TP3 que dispara fetch_url + LLM combo, el TPM va a apretar más. Confirmar si org bumpó tier antes de arrancar TP3.

## Aprendizajes para TP3

- **B1 commit gap pattern**: cualquier ARQ wrapper que delega a un sync helper que sólo hace `flush()` necesita commit explícito en el wrapper. F3 expuso el pattern; TP3 debe verificar que `pin_to_memory`, `fetch_url` worker (si hay) y cualquier nuevo persist path siguen el contrato. El test `_SessionCommitSpy` en `tests/shared/workers/test_brand_summary_regen.py` es reutilizable como patrón.
- **Lighthouse route-gated**: cualquier scenario TP3 que asuma "el copilot ya conoce la marca" debe correr en route allowlisted (`/offer-studio /landing /sales /growth-studio`). Si TP3 dispara desde `/dashboard`, brand_coherence va a degradar — testear desde superficies productivas.
- **ARQ result key dedupe stale**: cuando se fixea un worker bug y se quiere re-disparar la misma tenant_id+task, hay que limpiar `arq:result:{job_id}` manualmente o esperar `keep_result` expiry (~1h default). Sin esto, el re-enqueue es silently rejected. Para TP3, si tocás workers, agregar al playbook: `docker exec visionarias_redis redis-cli -n 0 DEL "arq:result:..."` antes de re-test.
