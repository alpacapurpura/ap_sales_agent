## Failures + root cause + fix aplicado

### B1 — Date parser regex no tolera prefijo "los/las/el/la" Spanish

- **Síntoma:** S4.3a primera corrida: "cuántas personas me escribieron en los últimos 30 días" devolvió **8** (esperado **15**). S4.3b mismo problema (conv 30d → 5, esperado ~50).
- **Trace evidence:** repro Python directo (`/tmp/tp4_diag.py`) mostró `intent.period_phrase='los últimos 30 días'` (LLM preserva prefijo verbatim). `parse_period` regex `^ultimos?\s+(\d+)\s+d(ias?|ays?)$` falla por leading "los " → fallback a `_default_window` = ISO week (7d). Todas las "30 días" colapsaron a 7d window.
- **Root cause:** `date_parser.py:140` regex anclada `^ultimos?…` no anticipa el artículo Spanish.
- **TDD fix:**
  - **RED:** `tests/modules/copilot/test_ask_tenant_data_date_parser.py::test_ultimos_n_dias_tolerates_leading_article` (parametrizado: "los últimos 30 días" / "los ultimos 30 dias" / "las últimas 30 días" / "el último 30 días").
  - **Arquitectura:** regex extendida `^(?:l(?:os|as)\s+|el\s+|la\s+)?ultim[oa]s?\s+(\d+)\s+d(ias?|ays?)$` — tolera artículo + género + acento mismatch.
  - **GREEN:** suite date_parser 23/23. Re-run S4.3a/b en BE retornó 15 + 52 ✅.

### B3 — `tool_call` trace event sin `duration_ms`

- **Síntoma:** primera corrida no permitió calcular latency p50/p95 del tool — todas las filas `tool_call` tenían `duration_ms IS NULL`.
- **Root cause:** `chat.py:1190` registra `acc.recorder.record(event_type="tool_call", ...)` sin pasar `duration_ms`. El recorder API soporta `duration_ms: int | None = None` pero el caller nunca lo populaba. Bug pre-existente F5+; TP4 fue el primero en intentar medir `tool_call.duration_ms`.
- **TDD fix:**
  - **RED:** `test_sse_v2_events.py::TestHandleToolEndV2BlockAppend::test_tool_call_trace_event_records_duration_ms` (fake recorder + acc.tool_started_at pre-populated 250ms ago + assert recorded duration ≥200).
  - **Arquitectura:**
    - `_StreamAccumulator.tool_started_at: dict[str, float] = field(default_factory=dict)` (run_id → monotonic).
    - `chat.py` stream loop: nuevo branch `event["event"]=="on_tool_start"` → `acc.tool_started_at[run_id] = time.monotonic()`.
    - `_handle_tool_end_v2`: lookup run_id → `duration_ms = int((time.monotonic() - start) * 1000)` → `recorder.record(..., duration_ms=...)`.
  - **GREEN:** test pasa + post-fix BE re-run muestra `tool_ms` populado en 9/9 turns (1862-3703ms range).

### B4 — `temperature=0.6` rompe Kimi K2.6 (HTTP 400 only-1-allowed)

- **Síntoma:** Post recreate container (Sprint 0 env activo), S4.1 devolvió `messages: []` + 0 tokens. Logs BE: `openai.BadRequestError: 400 - 'invalid temperature: only 1 is allowed for this model'`.
- **Root cause:** `deep_agent.py:139-142` hardcodea `temperature=0.6` para `ModelRole.AGENT`. Heredado A7 (`98d6fe7a`) cambió `KimiService._DEFAULT_TEMPERATURE = 1.0` pero el explicit kwarg override BYPASSEABA el default. Con AGENT=Kimi K2.6 cada turn rompe.
- **TDD fix:**
  - **RED:** `tests/shared/infrastructure/llm/test_openai_compat_providers.py::TestKimiService::test_k2_6_temperature_override_is_clamped_to_one`.
  - **Arquitectura:** `KimiService._get_chat_model` override que detecta `"k2" in model_name.lower()` + temperature ≠ 1.0 → coerce a 1.0 + emit `structlog.warning` "kimi_k2_temperature_clamped" (visible para diagnóstico). DeepSeek/Qwen sin afectar (no override base).
  - **GREEN:** suite 11/11 + factory tests actualizados (`test_deep_agent_factory_wire.py::test_temperature_override_is_applied` ahora usa `ModelRole.REASONING` para evitar clamp; nuevo `test_kimi_k2_temperature_clamped_for_agent_role` documenta la nueva invariante).
  - **Verificación runtime:** post recreate + restart BE post B4, S4.b2 batch (9 turns) corrió sin error 400. Trace muestra `data->>'model' = 'gpt-4o-mini-2024-07-18'` (último LLM call = synth), pero el AGENT main loop sí ejecutó Kimi (probado por la ausencia del 400).

### B0 (regresión collateral durante regression) — `_ScriptedLLM.invoke()` no acepta `config` kwarg

- **Síntoma:** suite `test_ask_tenant_data_integration.py` falló post B1+B3+B4 con `TypeError: _ScriptedLLM.invoke() got an unexpected keyword argument 'config'`.
- **Root cause:** Stub stale post-TP3 B1 (internal LLM tag pattern). El stub no se actualizó cuando intent_classifier empezó a pasar `config=INTERNAL_LLM_CONFIG`.
- **Fix:** `def invoke(self, messages, **_kwargs)` — absorbe config silently.
- Suite 7/7 verde post fix.

## Aprendizajes para TP5

- **Kimi K2.6 clamp pattern (B4)**: cualquier callsite que pase `temperature` explícita a `LLMFactory.get_client(role=AGENT, ...)` se beneficia del clamp. F6 workflows que construyan sus propios LLM clients (si lo hacen) deben usar `LLMFactory` y NO instanciar `ChatOpenAI` directo — sino el clamp se evade. Verificar pre-flight en TP5.
- **Date parser tolerance pattern (B1)**: el LLM intent_classifier preserva artículos Spanish verbatim ("los/las/el/la"). Cualquier regex futuro de date_parser o slot extraction debe anticipar prefijos de artículos. Aplicable a TP5 si workflows tienen período capture.
- **Tool latency observability (B3)**: el patrón "store start in acc → compute elapsed in handler" es replicable para cualquier nuevo evento que requiera duration_ms. F6 workflows pueden reusar `acc.tool_started_at` para sub-step timing si emiten su propio `event_type`.
- **Sanity-check ANTES ejecutar (lección TP3 reforzada)**: TP4 phase doc tenía 3 divergencias vs F5 real (NANO no FAST + tenant sin data + S4.5 unsupported). Detectarlas pre-execution ahorró ~30 min de "scenario falla por mala expectativa". TP5 debe leer F6 source code pre-research.
