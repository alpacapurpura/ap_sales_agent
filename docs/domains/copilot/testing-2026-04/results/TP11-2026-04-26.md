## Failures + root cause + fixes

### B23-TP11 — A2.1 voseo leak system prompts → user-facing output (FIX APLICADO TDD)

- **Síntoma:** J4 audit response user-facing contiene voseo (`Querés`, `podés`, `servís`, `competís`, `preferís`). Regla 11 hard fail. Output sanitizer B7-TP6 corrige tokens en post-procesado pero **el user los ve durante streaming SSE token-a-token** — el sanitizer no es streaming-aware.
- **Root cause arquitectónico:** `_DEEP_AGENT_SUFFIX_ES` (deep_agent.py:73-99) y `_URL_ANALYZER_PROMPT` (subagents/url_analyzer.py:32-51) contenían voseo (`anotá`, `Marcá`, `avanzás`, `querés`, `delegá`, `respondé`, `llamá`, `reportá`, `continuá`, `aprovechás`, `guardás`, `sugerís`, `devolvele`). Kimi K2.6 (AGENT tier) **arrastra el registro lingüístico del system prompt al output** (B11-TP6 phrasing-sensitive). Adicionalmente, los ejemplos negativos `"vos/tenés/podés"` literal en regla causan false positives detectables como voseo en use.
- **TDD fix aplicado:**
  - **(a) Test RED:** `tests/modules/copilot/test_deep_agent_prompt_voseo_compliance.py` — 4 tests (2 system prompts + 1 description + 8 parametrize sanity). Detecta 11 tokens voseo en `_DEEP_AGENT_SUFFIX_ES` + 7 tokens en `_URL_ANALYZER_PROMPT`.
  - **(b) GREEN fix:**
    - `deep_agent.py::_DEEP_AGENT_SUFFIX_ES` — voseo→tuteo (`anotá`→`anota`, `Marcá`→`Marca`, `avanzás`→`avanzas`, `querés`→`quieres`, `delegá`→`delega`, `respondé`→`responde`, `Usá`→`Usa`).
    - Refrasear regla negativa `(sin voseo, sin "che", sin "vos/tenés/podés")` → positiva (`Usa tuteo (tú, tienes, puedes, quieres) ... NO uses formas con acento final -ás/-és/-ís ni el pronombre rioplatense`).
    - `subagents/url_analyzer.py::_URL_ANALYZER_PROMPT` + description — voseo→tuteo (`llamá`→`llama`, `reportá`→`reporta`, `continuá`→`continúa`, `devolvele`→`devuélvele`, `aprovechás`→`aprovechas`, `guardás`→`guardas`, `sugerís`→`sugieres`, `usá`→`usa`).
  - **(c) GREEN confirm:** 11/11 voseo compliance tests PASS. 43/43 tests `test_deep_agent_*` + `test_output_sanitizer_*` PASS. Lint clean. Arch fitness 571/571 PASS.
  - **(d) Live re-validation:** restart `api_dev` + re-run J4 mismo prompt. **97% reducción voseo** (1 instance "Querés" en primer bloque subagent intermediate vs 5+ pre-fix). **Final user-facing answer 0 voseo.** Tuteo consistente: "construyas", "te recomiendo", "empecemos", "Quieres".
- **Regression coverage:** snapshot test scanner detecta 75+ voseo tokens via regex word boundary. Si futura iteración mete voseo en `_DEEP_AGENT_SUFFIX_ES` o `_URL_ANALYZER_PROMPT` o subagent description, CI falla.

### B22-TP11 — ProposalCard "Aplicar" silent no-op cuando activeBridge no connected (DEFERRED §4.4)

- **Síntoma:** J1 click "Aplicar" en ProposalCard → UI muestra status `applied` verde + texto "Aplicado". `copilot_mutation_journal` vacío. Form fields Brand Studio identity siguen vacíos post-click + post-reload. **No transparency al user que el save fue no-op**.
- **Root cause:** `ProposalCard.handleApply` (frontend `messages/ProposalCard.tsx:34`) requiere `activeBridge` form-runtime context para hacer `bridge.patchField(field.path, update.new_value)`. Si el bridge no está registrado en `useCopilotStore.getState().activeBridge`, **by design** el apply es no-op silencioso ("the chat still reports success so the user sees the visual confirmation, but nothing mutates outside the form" — JSDoc comment).
  - Brand Studio identity page tiene form-runtime mounted pero el bridge no se registra cuando el copilot panel está abierto en lateral, posiblemente porque el page no está activamente focused.
  - O: el sistema NO tiene fallback path para "apply directo via backend mutation API" cuando bridge unavailable.
- **Por qué deferred:** Cross-stack fix requiere:
  1. Frontend: investigar `useCopilotStore.activeBridge` registration logic + cuándo deregister.
  2. Frontend: agregar fallback `if (!bridge) → call /api/v1/copilot/.../mutations/apply` para forzar persist independiente.
  3. Backend: verificar/agregar mutations/apply endpoint si no existe (reqid=137 + 211 retornaron 404 — endpoint missing o auth).
  4. Frontend: si NO se puede persist, status NO debe ser "applied" verde — mostrar warning "no se pudo guardar, navega a la sección".
- **Excepción §4.4 invocada:** scope cross-stack > scope TP11 (UX testing, no full-stack debug). Documentado como F-pos crítico priorizado.

### B24-TP11 — `format_for_channel` tool NO se invoca por phrasing user implícito (DEFERRED §4.4)

- **Síntoma:** J2.T2 user "armame copy para WhatsApp" → copilot generates structure de oferta, NO invoca `format_for_channel` tool. J2.T3 explicit "copy WA literal sin asteriscos sin headers" → copilot pide más info. **H7 canal-aware fail consistent.**
- **Root cause:** No hay heurística que force binding de `format_for_channel` cuando user msg matches `(WhatsApp|email|sms|whatsapp|wa|copia.*pega)` patterns. El LLM debe descubrir que necesita el tool, pero no consistentemente lo hace para Kimi K2.6.
- **Por qué deferred:** requiere agregar middleware en `chat.py::_build_dynamic_tools` que detecta channel keywords + force-includes `format_for_channel` tool en bound set. F-pos arquitectónico middleware.

### B25-TP11 — Routing classifier NANO call sequencial bloquea TTFB (DEFERRED §4.4)

- **Síntoma:** TTFB block_start ~2770ms en J1.T1 (mensaje corto "hola"). Routing decision toma 2.76s **antes** del primer model node enter — durante este tiempo solo se emite SSE `event: status` thinking pero no text. >1500ms 2026 conversational breaking point.
- **Root cause:** `chat.py::_record_routing_decision` ejecuta LLMClassifier NANO call sequencialmente antes de bind tools + LLM call. No hay parallelism.
- **Por qué deferred:** F-pos optimización requiere refactor para correr classifier en background + warm-up LLM en paralelo, con coalescing al primer block_delta. Risk: race condition si tier change cambia bind_tools.
