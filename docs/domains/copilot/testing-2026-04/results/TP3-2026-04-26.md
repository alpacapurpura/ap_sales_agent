## Failures + root cause + fix aplicado

### B1 (TP3 nuevo) — Internal LLM streams leak as user-visible block_delta

- **Síntoma:** durante S3.1 turn 1 inicial, el block_delta SSE streameó la JSON envelope del analyzer (`{ "slug": "muj...", "summary": "...", ...}`) live al usuario antes de que el sanitizer la borrara en `block_end`. Flash-of-JSON visible.
- **Trace evidence:** stream events `on_chat_model_stream` capturaban tanto el modelo del agente como el LLM interno del analyzer (`url_inspiration_analyzer.analyze`). LangGraph `astream_events` instrumenta TODO chat model dentro del graph; sin tag distintivo, los tokens del analyzer entraban al canal de texto del usuario.
- **Root cause:** `_process_stream_event` en `chat.py::CopilotOrchestrator` no filtraba por origen. Tools que invocan LLMs internos (analyzer, synthesizer, intent_classifier) compartían el canal de stream del agente.
- **TDD fix:**
  - **RED:** `tests/modules/copilot/test_streaming_integration.py::test_on_chat_model_stream_with_internal_tag_is_dropped` + `..._in_metadata_is_dropped` (2 tests). Pre-fix: `text="{\"slug\": \"leak\""`; assert text is None falla.
  - **Arquitectura:**
    - Nuevo módulo `src/modules/copilot/application/orchestrator/stream_filters.py` con `INTERNAL_LLM_CONFIG = {"tags": ["copilot:internal"]}` + helper `is_internal_llm_event(event)` (chequea `tags` + fallback `metadata.tags`).
    - `chat.py::_process_stream_event` ahora dropea events con la tag.
    - 3 tools internos pasan `config=INTERNAL_LLM_CONFIG` a `llm.invoke(messages, config=...)`: `url_inspiration_analyzer`, `ask_tenant_data/synthesizer`, `ask_tenant_data/intent_classifier`.
  - **GREEN:** 4 tests nuevos en stream + 3 tests nuevos tool-side (cada tool valida que su `last_config["tags"]` contiene `copilot:internal`). Stubs `_StubLLM` aceptan kwarg `config` ahora.
- **Verificación runtime:** S3.1 v2/v3/v4 SSE muestra block_delta limpio, final markdown = "He guardado la página de Mujeres Coraje como inspiración. Su sección de testimonios destaca…" sin artefactos JSON.

### B2 (TP3 nuevo) — `inspiration_saved` + `memory_pinned` card_kind no registrados

- **Síntoma:** post B1, S3.1 todavía no producía `card_emitted` trace ni `block_append` SSE para la card. Sólo el legacy `tool_result` event que embebía el ui_action como string.
- **Root cause:** `_TYPE_TO_CARD_KIND` en `chat.py` no mapeaba `"inspiration_saved"` ni `"memory_pinned"`. F4 explícitamente difirió el FE renderer (learnings línea 85: "El JSON está estable, no requiere coordinación cross-stack para ese delivery") pero el efecto colateral era que el BE-side card pipeline tampoco se gatillaba.
- **TDD fix:**
  - **RED:** `tests/modules/copilot/test_streaming_integration.py::test_inspiration_saved_action_wraps_to_card_block` + `..._memory_pinned_action_wraps_to_card_block`.
  - **Arquitectura:**
    - `_TYPE_TO_CARD_KIND` extendido con `"inspiration_saved"` + `"memory_pinned"`.
    - `CardBlock.card_kind` Literal en `domain/message_blocks.py` extendido.
    - `CARD_PAYLOAD_MODELS` en `domain/card_payloads.py` extendido con `InspirationSavedCardPayload` + `MemoryPinnedCardPayload` (Pydantic v2, fields validados).
  - **GREEN:** 2 tests nuevos + suites existentes verde (`test_card_payload_schemas`, `test_message_blocks_exhaustive`).

### B3 (TP3 nuevo) — `ToolMessage` payload no parseable por tool_end handlers

- **Síntoma:** post B1+B2, todavía 0 `block_append` events. El typed-card pipeline NO se disparaba aunque el mapping era correcto.
- **Root cause:** `_handle_tool_end` y `_handle_tool_end_v2` en `chat.py` parseaban `tool_output` sólo si era `dict` o `str` directo. LangGraph + deepagents emiten `on_tool_end` con `output=ToolMessage(content="<json string>", ...)`. `parsed_output` quedaba `None` → ni el legacy `ui_action` event ni el v2 `block_append` se emitían. Bug pre-existente F2/F4 que sólo afloró cuando un tool con `ui_action` corrió bajo el deep-agent harness con tool-typing fuerte.
- **TDD fix:**
  - **RED:** `test_parse_tool_payload_unwraps_tool_message` + `test_parse_tool_payload_returns_none_on_garbled_content`.
  - **Arquitectura:** nueva helper `_parse_tool_payload(tool_output) -> dict | None` en `chat.py` que maneja `ToolMessage(content: str|list|dict)` + `dict` + `str`. Ambos handlers (v1 + v2) la usan.
  - **GREEN:** 2 tests nuevos verde + S3.1 SSE muestra `event: ui_action` + `event: block_append` + trace `card_emitted` 1:1 por fetch_url.

### B4 (TP3 nuevo) — Zombie assistant messages rompen turn 2 con OpenAI 400

- **Síntoma:** S3.2 turn 2 fallaba con `event: error` + log `openai.BadRequestError: 400 - tool_call_ids did not have response messages: call_HBqKmSBh1idxG5tW14LjXcgd`.
- **Trace evidence:** `copilot_conversations.messages` post-S3.1 contenía 5 rows en lugar de 4: user → assistant(tool_calls=[fetch_url]) → assistant(content="}") ← zombie → tool(call_HBq…) → assistant(prose). El `}` venía del sanitizer trimmeando JSON pre-B1; aún post-B1 alguna middleware del deep-agent emite un AIMessage extra que el persister captura.
- **Root cause:** `_serialize_messages` no filtraba AIMessages "vacíos" (content stripped ≤ 1 char) sin tool_calls. El zombie quedaba entre el assistant(tool_calls) y el tool response, violando la invariante OpenAI "every tool_call_id MUST be followed by a tool message".
- **TDD fix:**
  - **RED:** `test_serialize_messages_drops_zombie_assistant_artifact` (zombie filtered, sequence assistant→tool→assistant) + `test_serialize_messages_keeps_meaningful_short_assistant` (¡OK! preservado, no over-filter).
  - **Arquitectura:** filtro en `_serialize_messages`: `if not msg.tool_calls and len(stripped) <= 1: continue`.
  - **GREEN:** S3.1+S3.2 fresh conv (`b6e1e44c…`) tiene 4 rows limpias post-S3.1; turn 2 procesa OK, turn 3 cita inspiration sin re-fetch.

## Anomalías heredadas (sin fix arquitectónico)

### A1 — OpenAI quota exceeded (`insufficient_quota` HTTP 429)

- **Síntoma:** mid-S3.6 + S3.7 + S3.8 E2E, todas las llamadas chat fallaron con `event: error` + `openai.RateLimitError code=429 type=insufficient_quota`. Distinto a TP1 B2 (TPM tier 1): este es **billing-level quota agotada para la cuenta OpenAI** entera.
- **Impacto en TP3:** S3.6 segundo LLM no pudo ejecutarse (la verificación parcial del path tool=error sí pasó). S3.7 + S3.8 E2E rebajados a unit-level + DB-state validation.
- **Acción TP4:** confirmar status billing OpenAI antes de arrancar (recargar saldo / bumpear plan). TP4 también dispara LLMs intensivos (synthesizer + intent_classifier en cada `ask_tenant_data` call).
- **Mitigación si vuelve a pasar:** tener una key alternativa o usar Anthropic FAST tier de fallback (HEAVY ya está en Anthropic Opus).

## Aprendizajes para TP4

- **Internal LLM tag pattern (B1)**: cualquier tool que invoca un LLM como parte de su pipeline (intent_classifier, synthesizer en F5; cualquier helper en F-pos) DEBE pasar `INTERNAL_LLM_CONFIG` desde `src/modules/copilot/application/orchestrator/stream_filters.py`. Sin la tag, `astream_events` filtra los tokens al canal user-visible. F5 ya lo hereda en sus 2 tools post-B1.
- **ToolMessage parsing (B3)**: graph tools devuelven `ToolMessage` objects. Cualquier orquestador downstream que necesite leer `ui_action` o `status` del payload debe usar `chat._parse_tool_payload(tool_output)` (no `json.loads(str)` directo). F5 va a emitir cards (`metric_summary`, `data_query_result`?) que precisan este unwrap.
- **Phase doc sanity check**: antes de ejecutar un escenario, verificar que la API real del tool/feature coincide con lo que el escenario asume. S3.7 asumía `pin_to_memory(content="...")` pero la F4 real es `pin_to_memory(slug=...)`. TP4 hacer la misma verificación: si un escenario de `ask_tenant_data` asume natural language input pero la real es plan-shaped, ajustar phase doc primero.
