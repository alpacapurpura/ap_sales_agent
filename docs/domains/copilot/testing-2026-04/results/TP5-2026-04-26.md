## Failures + root cause + fix aplicado

### B7 — `_check_offer_completion` SQL `is_active` column inexistente

- **Síntoma:** S5.6 inicial post-restart container devuelve `event: error` mid-stream. Trace `tool_call: get_module_completion_status status=ok duration_ms=NULL` (no se grabó porque tool node escapó antes del recorder por exception). Logs BE: `psycopg2.errors.UndefinedColumn: column "is_active" does not exist` en `awareness.py:58`.
- **Root cause:** `awareness.py:_check_offer_completion` query `SELECT COUNT(*) FROM products WHERE tenant_id=:tid AND is_active = true` — pero `products` table tracked lifecycle via `status` (enum) + `deleted_at` + `archived_at`. Column `is_active` nunca existió. Bug pre-existente F0+ cubierto por except narrow `(TypeError, ValueError)` que NO captura `SQLAlchemyError` → propagated y crashed chat turn.
- **Aggravante:** rule `copilot-resilience.md` "nunca swallow exceptions silently" violada por el opposite — el except era TAN narrow que el ProgrammingError pasó arriba sin handling.
- **TDD fix:**
  - **RED:** `tests/modules/copilot/test_awareness_offer_completion.py` — 4 tests parametrizados (alive/archived/deleted/empty/sqlalchemy_error). Primer run falla con `OperationalError: no such column: is_active`.
  - **Arquitectura:**
    - SQL filter aligned con partial index `ix_products_active_by_tenant`: `WHERE tenant_id=:tid AND deleted_at IS NULL AND archived_at IS NULL`.
    - Except broadened a `Exception` con `logger.exception` + tenant_id/error tags — graceful degradation per `copilot-resilience.md` (chat turn no 500 en schema drift, log via Sentry).
  - **GREEN:** suite 4/4 verde.

### B8 — Kimi K2.6 thinking mode + post-tool re-invocation 400

- **Síntoma:** S5.6 v2 post-B7 fix devuelve nuevo `event: error`. Trace muestra `tool_call: get_module_completion_status status=ok duration_ms=38` + `card_emitted: checklist` correctos, pero `node_enter: model` (segunda invocación post-tool) explota. Logs: `openai.BadRequestError: 400 - thinking is enabled but reasoning_content is missing in assistant tool call message at index 2`.
- **Root cause:** Kimi K2.6 con thinking mode (default server-side) requiere `reasoning_content` en cada assistant message del history que llevó tool_calls. LangChain no preserva ese campo cuando re-envía el message history para el post-tool synthesis call. Cualquier turn con ≥1 tool call + post-tool re-invoke explota.
- **Reconciliación con B4:** B4 clampaba a `temperature=1.0` porque Kimi K2.6 thinking-enabled solo acepta 1.0. Pero Kimi K2.6 con thinking deshabilitado tiene constraint diferente: solo acepta `temperature=0.6`. Después de fixear B8 (disable thinking), el clamp B4 se vuelve incorrecto — produce nuevo 400 "only 0.6 is allowed".
- **TDD fix:**
  - **RED:** `tests/shared/infrastructure/llm/test_openai_compat_providers.py::test_k2_6_disables_thinking_mode` — assert `client.model_kwargs["extra_body"]["thinking"] == {"type": "disabled"}`. Falla pre-fix.
  - **Arquitectura:**
    - `KimiService._get_chat_model`: forzar `model_kwargs["extra_body"] = {..., "thinking": {"type": "disabled"}}` para todo modelo K2.
    - Renombrar y re-tarjetar B4 clamp: ahora clamp a `_K2_REQUIRED_TEMPERATURE = 0.6` (el valor exigido por server con thinking off, vs 1.0 con thinking on). Comentario detalla ambos regímenes.
    - `_DEFAULT_TEMPERATURE` bumped 1.0 → 0.6 (consistencia con regimen post-B8).
    - Tests `test_k2_6_temperature_override_is_clamped_to_one` renombrado a `test_k2_6_temperature_clamped_to_required_value` — clampear a 0.6 (era 1.0).
    - `test_kimi_k2_temperature_clamped_for_agent_role` (factory wire) actualizado idem.
  - **GREEN:** Kimi suite 12/12 + factory 6/6 + arch + workflow F6 → 644/644 verde. Live S5.6 post-restart turn completa OK con 4 POST a moonshot 200 OK.
  - **Trade-off documentado:** Sin reasoning_content visible en trace events ni storage. Re-enable thinking + plumb reasoning_content cuando chain-of-thought visibility entre roadmap (probable F-housekeeping post-cutover).
