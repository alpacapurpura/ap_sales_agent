## Sub-bugs descubiertos durante FP3

> Append-only.

### Sub-FP3.1 — Observación: tier es telemetría pura, NO afecta routing efectivo

- **Hallazgo:** Durante implementación se confirmó que `tier_selected` en `copilot_routing_log` es **telemetría observability/cost analysis exclusivamente**. La selección efectiva de modelo en el graph runtime es invariante: `build_deep_agent_graph` línea 189 hardcodea `LLMFactory.get_client(ModelRole.AGENT, temperature=0.6)`. Tools binding tampoco usa tier — `get_tools_for_context` resuelve por route + guided flag. Esto SIMPLIFICA brutal el FP3: NO hay race condition real entre routing decision y bind, así que el patrón "speculative bind superset + swap mid-flight" del phase doc es **innecesario**. Fire-and-forget background task suficiente.
- **Impacto:** AC4 race-condition guard se reduce a confirmar coherencia del row persisted. Test cobertura intacta. Riesgo cero para `tools_available` en bound set.
- **Decisión:** mantener tier en routing_log como telemetría — informa el dashboard admin para analizar si `ModelRole.AGENT` (Kimi K2.6) está siendo over/under-utilized vs sub-loaded categories. Cuando F-tier sprint avance (post-MVP) podría wirear tier→model dinámico, pero NO en F-pos batch.

### Sub-FP3.2 — DEFERRED: rule-path TTFB no destrabable más

- **Síntoma:** En messages cortos (≤40 chars o keyword match), el rule classifier responde en 6-8ms — no hay nada que paralelizar. TTFB rule path pre/post ~57-150ms. La latencia restante (40-130ms) viene de `PatchToolCallsMiddleware.before_agent` (deepagents middleware stack) + Python overhead de spawn de graph.
- **Workaround:** ya está bajo target 800ms por orders of magnitude.
- **Plan:** si futuras heuristics 2027 piden TTFB <50ms, evaluar lazy-compile del deep_agent graph (`@cached_property` middleware stack reutilizable cross-turn) o pre-warm pool. NO en F-pos.

### Approach patterns que funcionaron

1. **TDD inline RED → GREEN → live re-validation 25 min ciclo.** Replicado en los 3 FPs (FP1/FP2/FP3) sin pain. Pattern reusable: write failing test, fix arquitectura, run tests GREEN, restart api_dev, curl + SQL probe trace events.

2. **System prompt hint = wiring barato (~400 tokens), latency cero** vs tool_choice programmatic (más invasivo). FP2 confirmó pattern; FP3 lo confirma de nuevo: la solución más simple es la que NO toca el contract de la lib subyacente.

3. **Phrasing-sensitive Kimi K2.6 = imperative + explícito + ejemplo.** Tu nudge al LLM tiene que ser contrato, no sugerencia (FP2 insight). FP3 no lo necesitó pero está validado para futuros nudges.

4. **Tier=telemetría puro, model_role hardcoded** evita race conditions ficticios. Cuando un campo se usa solo para observability/cost analysis, NO es safe-critical y puede correr fire-and-forget. Pattern reusable para FP4+ donde haya datos "info-only".

5. **Native-first WSL** (lint/tests) + Docker only para runtime + restart api_dev + live curl + SQL probe = ciclo de feedback más corto que cualquier intento de E2E Playwright para BE-only fixes.

## Aprendizajes meta del batch F-pos

1. **Cross-stack bugs requieren cross-stack fixes** (FP1) pero la mayoría de "UX bugs" del redesign-2026-04 fueron BE-only (FP2/FP3) porque FE shells ya estaban correctos — el LLM behavior + orchestrator wiring eran el bottleneck. Pattern: cuando UX falla en plataforma con LLM en el medio, mira primero el orchestrator + system prompt antes que el FE.

2. **TP testing as exploration + FP fixing as validation** dividen el trabajo bien. TPs descubren bugs reales en journeys live; FPs los cierran con TDD + before/after evidence. NO mezclar — el TP no debe arreglar (fuera de hot-path inline) y el FP no debe explorar nuevos journeys.

3. **El feedback loop más corto = SQL probe `copilot_trace_event` + curl native.** Chrome DevTools MCP es excelente para reproducir reportes de usuario, pero para TDD architectural fix (FP3 latency, FP2 middleware, FP1 mutation persist) la combinación SQL + curl es 5x más rápida.

4. **Documentar antes de cerrar** — los `results/FP{N}.md` con before/after evidence + métricas + sub-bugs descubiertos + handoff prompt son lo que permite que el siguiente FP arranque sin re-leer todo. ROI documentación >>> ROI código adicional.
