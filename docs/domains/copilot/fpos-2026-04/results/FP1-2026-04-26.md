## Pre-research

| Query | Insight clave | Aplicación |
|---|---|---|
| `react form-runtime bridge pattern 2026 dispatcher subscriber fallback` | TanStack Form + React 19 useSyncExternalStore subscribe-to-slice. fallback = recompute reducer base state + dispatched queue. Bridge no listed standard primitive — proyecto define su propio contract. | `FormRuntimeBridge` ya define `getSnapshot`/`patchField`/`subscribe` (locked en FLOW-SPEC §3.4). Fallback path BE = decisión local — no library default a copiar. |
| `FastAPI mutation endpoint idempotent apply pattern 2026` | 2 patterns: header `Idempotency-Key` (client UUID + server cache) o natural-key dedupe (server-side). idemptx + asgi-idempotency-header librerías Redis. | Elegido **natural-key** (`(tenant, conv, message, field_path)`) — más simple, sin Redis, idempotency vivo en DB partial unique index. Repeated clicks misma proposal → mismo journal row. |
| `optimistic UI rollback strategy 2026 mutation failure status feedback` | TanStack DB v5: optimistic apply + handler invocation + recomputeOptimisticState() on failure. React 19 useOptimistic = partial rollback "keep change visible but marked failed". | Patrón aplicado: ProposalCard `status: pending → applying → applied|failed`. Failed expone Reintentar + alert visible (no silent revert). |

## Sub-bugs descubiertos durante FP1

### Sub-FP1.1 — DEFERRED: handlers offer/buyer_persona side-effect

- **Síntoma:** apply endpoint con `field_id="public_name"` (offer) o `field_id="story.origin_story"` (buyer_persona) → journal row creado pero aggregate NO actualizado. Reload page → valor antiguo.
- **Scope:** crear `OfferFieldApplyPort` + `BuyerPersonaFieldApplyPort` + adapters. Cada uno needs `entity_id` (offer ID / persona ID) que hoy NO viene en `ProposalUpdate` payload. ProposalCard + propose_field_updates tool deben extender shape para incluir `entity_id`.
- **Workaround:** journal row sigue persistiendo (audit trail intacto). Bridge happy path sigue funcionando para offer/persona (AC1) — solo el fallback (AC2) está limitado al brand domain en FP1.
- **Plan:**
  1. Extender `propose_field_updates` para emitir `entity_id` cuando aplica.
  2. Agregar `entity_id?: UUID` a `ProposalUpdate` (FE) + `ApplyMutationUpdate` (BE DTO) + `MutationApplyService` propaga al handler.
  3. Implement `OfferFieldApplyAdapter` + `BuyerPersonaFieldApplyAdapter`.
  4. Migration N/A — journal table ya soporta `entity_id`.

### Sub-FP1.2 — DEFERRED: streaming proposal emit no incluye `assistant_message_id` en SSE payload

- **Síntoma:** ProposalCard fallback necesita `messageId` para idempotency natural key. Hoy se infiere via `messageId` prop pasado por CardBlock/AssistantMessage. Si proposal viene en SSE payload sin que el message tenga ID estable (e.g. AssistantMessage genera ID FE-side), idempotency degrada.
- **Workaround:** AssistantMessage existing genera IDs estables FE-side por turno — funciona en happy path TP11.
- **Plan FP2 / FP3:** verificar emisión SSE ya emite `message_id` consistente. Si no, refuerzo en `chat.py` orchestrator.

### Sub-FP1.3 — Anomalía heredada: 2 tests pre-existentes flaky

- `tests/modules/copilot/test_ask_tenant_data_integration.py::test_conversation_count_question` — `assert 1 == 3` reproducible isolated (no flakiness, bug real desde TP4 commit `08894f7a`). NO introducido FP1.

- `tests/modules/copilot/golden/test_baseline_route_tools.py::test_route_tool_selection_matches_baseline` — pasa isolated, falla en suite full → ordering issue.

## Aprendizajes para FP2

1. **F1 ratchet `test_no_new_copilot_module_imports` se viola fácil con direct repo import.** Cualquier handler nuevo en `copilot/application/services/handlers/` DEBE pasar via port en `shared/links/ports/`. Adapter vive en `{domain}/application/services/{name}_field_apply_adapter.py`. Patrón replicable para FP2 si introduce dispatcher por canal (e.g. `ChannelOutputPort`).

2. **`MutationApplyService` ya wirea handler registry — para FP2 podés colgarte de mismo pattern si necesitás per-channel formatter.** `register_apply_handler` exporta API estable. Ej: `register_format_handler("whatsapp", whatsapp_formatter)`.

3. **TDD inline + live curl + SQL probe = ciclo de 25 min tipo B23-TP11.** Replicado FP1 sin pain. RED tests ANTES código, GREEN al cerrar capa, live re-validation con SQL probe es prueba-de-fuego más barata que Chrome DevTools E2E. **Recomendado FP2 mismo flow:** test_chat_routing_keyword_detection.py RED → middleware → live curl con `{"message":"armame copy WhatsApp"}` → SQL probe `copilot_trace_event WHERE name='format_for_channel'`.
