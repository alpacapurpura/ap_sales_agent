## Implementation Decisions

### Playground Structure
- Atomic hierarchy navigation: Tokens (colors, typography, spacing) → Atoms (Button, Input, Badge...) → Molecules (FormField, Card with actions...) → Organisms (DataTable, composed forms...)
- Sidebar navigation reflecting the Design System hierarchy directly
- Each component shown with: visual render, props/variants table, usage example

### Audit Scope
- Audit + Playground only — NO refactoring of existing components in this task
- Create a diagnostic document (AUDIT.md or similar) listing ALL inconsistencies, duplications, and issues found
- This document serves as the input for a follow-up `gsd:quick` task that will do the actual refactor
- Show components AS-THEY-ARE today, warts and all

### Component Inheritance Pattern (Claude's Discretion — AI-oriented)
- **CVA + Tailwind** (already integrated with Shadcn) as the base pattern
- Add a **component registry/manifest** (machine-readable JSON or TS) that Claude can read before generating any new component
- Registry should list: component name, atomic level, available variants, props, file path
- This is optimized for AI consumption: before creating anything new, Claude reads the registry to check what exists and how it's built
- The registry doubles as the data source for the Playground page itself
- **Why AI-oriented:** The user's primary concern is that AI (Claude) generates inconsistent components because there's no single source of truth. A machine-readable registry solves this directly.

### Claude's Discretion
- Playground page layout and visual design details
- Specific categorization of each existing component into atomic levels
- Format of the diagnostic document
