# Working Backwards (Amazon)

> Antes construir, escribí el press release + FAQ del producto terminado. Si la PR no excita, el feature no debe existir.

## Press release template (1 página)

```
## {Headline} — Headline irresistible 1 línea

## {Subheadline} — quién es para, beneficio principal

## Lead — 1 párrafo
Ciudad, fecha. {Empresa} anuncia {producto/feature}, que permite a {audiencia} {beneficio principal}.

## Problema — 1 párrafo
Hoy, {audiencia} enfrenta {problema}. Esto causa {consecuencia frustrante}.

## Solución — 1 párrafo
{Producto} resuelve esto al {cómo, mecanismo}. Ahora {audiencia} puede {nuevo capability}.

## Quote ejecutivo — 1 quote
"{Frase visionaria del founder/CEO}" — {nombre, cargo}.

## Cómo empezar — 1 párrafo
{Audiencia} pueden comenzar {acción concreta de adopción}.

## Quote cliente — 1 quote
"{Frase aspiracional de cliente imaginario describiendo cambio en su vida}" — {nombre cliente, rol}.

## Call to action — 1 línea
Visite {URL} para más info.
```

## Internal FAQ (5-10 preguntas duras)

Anticipá objeciones de stakeholders/builders:
- ¿Por qué este producto y no [alternativa]?
- ¿Cuánto cuesta construirlo?
- ¿Qué pasa si los users no lo adoptan?
- ¿Cómo nos compara con [competidor]?
- ¿Cuál es el flujo crítico end-to-end?
- ¿Qué métricas determinan éxito?

## Cuándo usar

| Situación | Veredicto |
|---|---|
| PI nuevo grande (módulo nuevo) | ✅ obligatorio |
| Refinamiento dentro PI | opcional |
| Bug fix / mejora pequeña | innecesario |
| Cambio estratégico producto | ✅ obligatorio |

## Por qué funciona

Forzás claridad de comunicación. Si no podés escribir la PR, no entendés el valor. Si la PR es aburrida, el feature también lo es.

## Anti-patterns

- ❌ Escribir PR para justificar feature ya decidido (= teatro)
- ❌ PR vague ("mejora UX") sin headline impactante
- ❌ Skip FAQ interno (= no anticipaste objeciones)
